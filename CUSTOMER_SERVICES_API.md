# Customer Services API

This contract is the boundary between `flutter-katolin` (the customer app) and the Django marketplace backend.

The customer app never connects directly to Sanaacash and never receives Sanaacash credentials, provider URLs, `userid`, username or password.

## Base

Production API:

`https://shopik.alattab.site/api/v2/services/`

Authentication uses the same authenticated application session as the rest of the marketplace API:

`Authorization: Token <customer-token>`

## 1. Service catalog

`GET /catalog/`

Returns the complete customer-facing hierarchy:

`main category -> service category -> child category -> service -> item/plan/denomination`

Every service contains only the fields the customer is expected to supply. Provider-generated values such as `num`, `packageid`, `external_code`, `uniqcode` and item-derived `amount` are generated by the backend from the selected catalog item.

The catalog is therefore suitable for a generic UI: the app does not need hardcoded provider forms.

## 2. Service request

`POST /requests/`

Headers:

- `Authorization: Token <customer-token>`
- `Idempotency-Key: <unique-request-id>`

Body:

```json
{
  "service_id": 123,
  "item_type": "telecom_plans",
  "item_id": 456,
  "payload": {
    "mobile": "774541452",
    "method": "New"
  },
  "idempotency_key": "client-generated-uuid"
}
```

The backend validates the declared service fields, resolves the selected catalog item, calculates the amount from the authoritative item price when applicable, reserves customer funds, creates a transaction and queues provider execution.

## 3. Examples

### Yemen Mobile balance

Service pricing mode: `amount`.

Customer fields:

```json
{
  "mobile": "774541452",
  "amount": "1000"
}
```

There is no customer-selected package branch for ordinary Yemen Mobile balance.

### Yemen Mobile package activation

The customer selects one package item. The app sends `item_id`/`item_type` and only the business fields such as the mobile number and activation method. The backend derives the provider package code and sends the exact contract parameters upstream.

### Game top-up

Hierarchy:

`الألعاب -> Free Fire/PUBG/... -> service -> package (for example 60 diamonds)`

Customer fields can include `playerid`, optional `playername`, optional `zoneid` and optional email, while the package's provider code is server-generated from the selected game product.

## 4. Operation result

The request returns the backend transaction id, service code, status, amount/currency and provider identifiers when they become available.

Typical lifecycle:

`accepted -> queued -> processing/pending_provider -> success`

or

`... -> failed/manual_review`

The customer app displays the backend status; it does not interpret Sanaacash responses itself.

## 5. Provider isolation

Provider configuration lives only in Django:

`ProviderConnection -> ProviderLink -> ServiceDistribution`

A Sanaacash connection stores the base URL, `userid`, domain name, username and encrypted password. The provider adapter generates the Sanaacash MD5 token and executes the configured link.

A future provider can be added through another connection/link without changing the customer app contract.

## 6. Source authority

The current Sanaacash provider mappings are based on `api 1 (59).pdf`. When legacy database values and the current provider contract conflict, the current API contract is authoritative for executable operations. Legacy-only records can remain in the catalog as reviewable data but are not automatically assigned to a live provider link.
